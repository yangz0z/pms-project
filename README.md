# 재고 점유 기반 숙소 예약 시스템

숙소 자사 예약 사이트에서 같은 객실이 이중으로 판매되지 않도록, 결제하는 동안 재고를 임시로 점유하고 결제가 끝나면 예약을 확정하는 시스템입니다.

## 해결하려는 문제

객실이 1개 남았을 때 두 고객이 동시에 결제를 시작하면 두 결제가 모두 성공할 수 있습니다. 이럴 경우 한 고객에게 연락해 양해를 구한 뒤 환불하는 과정이 필요하고, 고객은 결제까지 마친 예약이 취소될 수 있습니다.

이 프로젝트는 다음을 목표로 합니다.

- 마지막 객실에 예약 신청 20건이 동시에 들어와도 점유는 1건만 성공
- 결제 결과 알림이 중복으로 도착해도 확정은 1번만 처리
- 재고보다 많은 예약이 확정되는 경우 0건
- 결제가 끝났는데 객실이 없으면 그 상태로 두지 않고 환불 상태로 기록

## 전제

- 자사 예약 사이트를 대상으로 합니다.
- 이 시스템이 관리하는 객실은 OTA에 배정하지 않고 자사 사이트 판매용입니다.
- 판매 대기 점유 시간은 10분입니다.
- 예약은 체크인 전날까지 받습니다.
- 한 번에 최대 30박까지 예약할 수 있습니다.

## 구현 범위


| 포함                  | 제외             | 제외한 이유                                             |
| ------------------- | -------------- | -------------------------------------------------- |
| 예약 신청과 재고 점유        | 실제 결제 연동       | 검증 대상은 결제 결과를 받은 뒤의 정합성이므로 API 호출로 대체              |
| 결제 결과 수신과 예약 확정     | 실제 결제사 환불 호출   | 환불 요청 저장과 재시도까지 구현하고, `RefundGateway` 뒤의 실제 호출만 제외 |
| 점유 만료 처리            | 대형 OTA 재고 동기화  | OTA가 판매한 뒤 예약을 전달하는 구조에서는 점유 방식으로 막을 수 없음          |
| 신청 재전송과 결제 알림 중복 처리 | 객실 번호 배정       | 고객이 사는 단위는 객실 타입이고, 번호는 체크인 전에 배정 가능               |
| 동시 요청 테스트           | 요금 관리, 인증과 권한, 화면 | 이중 판매 방지와 직접 관련이 없음                                |


## 동작 방식

디럭스룸 11/10 ~ 11/12에 재고가 1개 남은 경우의 예시입니다.


| 상황                | 결과                           | 가용 재고 |
| ----------------- | ---------------------------- | ----- |
| 첫 번째 고객 신청        | `HOLD`                       | 1 → 0 |
| 점유 중 다른 고객 신청     | `409 TEMPORARILY_HELD`       | 0     |
| 결제 성공 알림 수신       | `CONFIRMED`                  | 0     |
| 같은 결제 성공 알림 재수신   | 무시                           | 0     |
| 결제 없이 10분 경과      | `EXPIRED`                    | 0 → 1 |
| 모두 확정된 뒤 다른 고객 신청 | `409 SOLD_OUT`               | 0     |
| 만료 후 결제 성공, 재고 남음 | 재고를 다시 잡고 `CONFIRMED`        | 1 → 0 |
| 만료 후 결제 성공, 재고 없음 | `REFUNDED`                   | 0     |
| 확정된 예약에 다른 결제 도착  | 그 결제만 환불, 예약은 `CONFIRMED` 유지 | 0     |


결제는 성공했지만 객실 확보에 쓰이지 못하면 환불합니다.

- A의 점유가 만료되어 재고가 복구된 뒤 B가 같은 객실을 점유했고, A의 결제 성공이 뒤늦게 도착하면 A의 결제를 환불합니다.
- 결제창을 두 번 열어 결제가 2건 성공하면 먼저 도착한 결제로 예약을 확정하고, 나중에 도착한 결제만 환불합니다.
- 이미 환불 처리된 예약에 다른 결제가 도착하면 그 결제도 환불합니다.

예약 상태 `REFUNDED`는 환불을 결정했다는 뜻이고, 실제 처리 결과는 `refund_request`에 남습니다.

만료와 결제가 동시에 발생하면 예약 행 잠금을 먼저 잡은 쪽을 기준으로 처리하므로 재고가 어긋나지 않습니다.

### 예약 날짜 변경

겹치는 날짜는 그대로 두고, 새로 필요한 날짜만 검증합니다. 전부 성공하면 빠지는 날짜의 재고를 풀고, 실패하면 기존 예약을 유지합니다.


| 변경                          | 검증 후 추가      | 해제           | 유지           |
| --------------------------- | ------------ | ------------ | ------------ |
| 11/10 ~ 11/12 → 11/9 ~ 11/11  | 11/9         | 11/11        | 11/10        |
| 11/10 ~ 11/12 → 11/10 ~ 11/13 | 11/12        | 없음           | 11/10, 11/11 |
| 11/10 ~ 11/13 → 11/10 ~ 11/12 | 없음           | 11/12        | 11/10, 11/11 |
| 11/10 ~ 11/12 → 11/20 ~ 11/22 | 11/20, 11/21 | 11/10, 11/11 | 없음           |


## 주요 설계 판단

- 재고를 신청 시점에 점유해, 결제 후 실패하는 일을 막음
- 재고 행을 날짜순으로 잠가 교착을 막음
- 환불 요청을 예약과 함께 저장한 뒤 호출해, 장애에도 환불이 누락되지 않게 함

## 실행 방법

Docker가 필요합니다.

```bash
docker compose up -d --build
```

`8989` 포트로 실행되며, 데모용 디럭스룸(`roomTypeId: 1`) 재고가 2030-11-10, 2030-11-11에 1개씩 준비됩니다.

테스트는 Testcontainers로 실제 PostgreSQL을 띄워 실행합니다. 동시성은 인메모리 데이터베이스가 아닌 PostgreSQL에서 확인해야 하기 때문입니다. JDK 21과 Docker가 필요합니다. 재고 행 잠금을 제거하면 동시 신청 테스트가 실패하는 것을 확인했습니다.

```bash
./gradlew test
```

마지막 객실에 20건을 동시에 신청하는 데모는 다음과 같이 실행합니다. 다시 실행하려면 `docker compose down -v`로 재고를 초기화한 뒤 서버를 다시 띄웁니다.

```bash
./scripts/demo-concurrent-holds.sh
```

```text
== 예약 신청 20건 동시 전송
HOLD 1건, TEMPORARILY_HELD 19건
== 결제 성공 알림
{"reservationId":1,"status":"CONFIRMED","duplicate":false}
== 같은 결제 성공 알림 재수신
{"reservationId":1,"status":"CONFIRMED","duplicate":true}
== 확정 후 다른 고객 신청
{"code":"SOLD_OUT","message":"예약이 모두 찼습니다."}
```

## 한계

- 대형 OTA에서 같은 객실을 함께 판매하면 이 시스템만으로는 이중 판매를 막을 수 없습니다.

- 점유 만료 작업은 서버 1대를 기준으로 합니다.
- 결제 실패 알림은 받지 않으므로, 결제에 실패한 점유는 10분이 지나야 풀립니다.
- 실제 결제사를 연동하는 범위는 제외했습니다. 연동하려면 알림 서명 검증, 환불 요청 멱등성 보장 여부 등을 추가로 검토해야 합니다.
- 인증과 권한은 과제 범위에서 제외했습니다.
- 예약 날짜 변경은 요금을 다루지 않습니다.
- 객실 타입 변경과 체크인 이후의 날짜 변경은 지원하지 않습니다. 이미 숙박 중인 고객의 연장도 여기에 포함됩니다. 날짜 변경의 `requestKey` 확인은 간단한 소유 확인이며 인증을 대신하지 않습니다.

## 기술 스택

Kotlin, Spring Boot, Spring JDBC(`JdbcClient`), PostgreSQL, Flyway, JUnit 5, Testcontainers
