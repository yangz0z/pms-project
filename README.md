# 재고 점유 기반 숙소 예약 시스템

숙소 자사 예약 사이트에서 같은 객실이 이중으로 판매되지 않도록, 결제하는 동안 재고를 임시로 점유하고 결제가 끝나면 예약을 확정하는 시스템입니다.

## 해결하려는 문제

객실이 1개 남았을 때 두 고객이 동시에 결제를 시작하면 두 결제가 모두 성공할 수 있습니다. 이럴 경우 한 고객에게 연락해 양해를 구한 뒤 환불하는 과정이 필요하고, 고객은 결제까지 마친 예약이 취소될 수 있습니다.

이 프로젝트는 다음을 목표로 합니다.

- 마지막 객실에 예약 신청 20건이 동시에 들어와도 점유는 1건만 성공
- 결제 결과 알림이 중복으로 도착해도 확정은 1번만 처리
- 재고보다 많은 예약이 확정되는 경우 0건
- 결제가 끝났는데 객실이 없으면 그 상태로 두지 않고 환불 상태로 기록

## 전제

- 자사 예약 사이트를 대상으로 합니다.
- 이 시스템이 관리하는 객실은 OTA에 배정하지 않고 자사 사이트 판매용입니다.
- 판매 대기 점유 시간은 10분입니다.
- 예약은 체크인 전날까지 받습니다.
- 한 번에 최대 30박까지 예약할 수 있습니다.

## 구현 범위


| 포함                  | 제외             | 제외한 이유                                    |
| ------------------- | -------------- | ----------------------------------------- |
| 예약 신청과 재고 점유        | 실제 결제 연동       | 검증 대상은 결제 결과를 받은 뒤의 정합성이므로 API 호출로 대체     |
| 결제 결과 수신과 예약 확정     | 실제 환불 처리       | 예약 상태를 `REFUNDED`로 기록하는 데까지만 구현           |
| 점유 만료 처리            | 대형 OTA 재고 동기화  | OTA가 판매한 뒤 예약을 전달하는 구조에서는 점유 방식으로 막을 수 없음 |
| 신청 재전송과 결제 알림 중복 처리 | 객실 번호 배정       | 고객이 사는 단위는 객실 타입이고, 번호는 체크인 전에 배정 가능      |
| 동시 요청 테스트           | 요금 관리, 로그인, 화면 | 이중 판매 방지와 직접 관련이 없음                       |


## 동작 방식

디럭스룸 11/10~11/12에 재고가 1개 남은 경우의 예시입니다.


| 상황                | 결과                     | 가용 재고 |
| ----------------- | ---------------------- | ----- |
| 첫 번째 고객 신청        | `HOLD`                 | 1 → 0 |
| 점유 중 다른 고객 신청     | `409 TEMPORARILY_HELD` | 0     |
| 결제 성공 알림 수신       | `CONFIRMED`            | 0     |
| 같은 결제 성공 알림 재수신   | 무시                     | 0     |
| 결제 없이 10분 경과      | `EXPIRED`              | 0 → 1 |
| 모두 확정된 뒤 다른 고객 신청 | `409 SOLD_OUT`         | 0     |
| 만료 후 결제 성공, 재고 남음 | 재고를 다시 잡고 `CONFIRMED`  | 1 → 0 |
| 만료 후 결제 성공, 재고 없음 | `REFUNDED`             | 0     |
| 확정된 예약에 다른 결제 도착  | 그 결제만 환불, 예약은 `CONFIRMED` 유지 | 0     |


## 설계 판단

### 재고를 신청 시점에 점유

결제 후에 재고를 차감하면 늦게 결제한 고객은 돈을 낸 뒤에 실패합니다. 신청 시점에 점유하면 결제 전에 거절할 수 있습니다. 대신 결제하지 않는 고객이 최대 10분 동안 재고를 묶습니다.

### 실패 사유를 두 가지로 구분

점유 때문에 재고가 없으면 잠시 뒤 예약이 가능할 수 있고, 확정으로 재고가 없으면 기다려도 예약할 수 없습니다. 고객에게 필요한 안내가 다르므로 응답을 나눕니다.


| 응답 코드              | 조건                                             | 안내                            |
| ------------------ | ---------------------------------------------- | ----------------------------- |
| `TEMPORARILY_HELD` | 모든 숙박일에 확정되지 않은 객실이 있으나 점유 때문에 가용 재고가 없는 날이 있음 | 잠시 후 다시 시도 (`Retry-After` 포함) |
| `SOLD_OUT`         | 숙박일 중 하루라도 확정으로 만실이거나 판매하지 않는 날짜 포함           | 다른 날짜 선택                      |


### 날짜순으로 재고 행을 잠금

연박 신청은 숙박일별 재고 행을 함께 변경합니다. 겹치는 기간의 요청이 서로 다른 순서로 행을 잠그면 deadlock이 생길 수 있어, `SELECT ... ORDER BY stay_date FOR UPDATE`로 항상 날짜순으로 잠급니다. 잠근 뒤 읽은 값으로 실패 사유도 판단합니다.

### 중복 요청은 유니크 제약으로 처리

- 신청 재전송: `reservation.request_key`
- 결제 알림 중복: `payment_event.payment_id`

애플리케이션의 사전 조회만으로는 동시에 들어온 두 요청을 막을 수 없어 데이터베이스 제약을 기준으로 삼습니다.

## 코드 구조

업무 단위로 패키지를 나눴고, 의존 방향은 `payment → reservation → inventory` 한 방향입니다.

| 패키지 | 책임 | 주요 클래스 |
|---|---|---|
| `inventory` | 재고 판단과 수량 변경 | `StayPeriod`, `DailyInventory`, `StayInventory`, `InventoryRepository` |
| `reservation` | 예약 상태 전이, 점유, 만료, 결제 반영 | `Reservation`, `ReservationService`, `HoldExpirer`, `ReservationSettlement` |
| `payment` | 결제 알림 중복 처리와 환불 요청 | `PaymentService`, `PaymentEventRepository`, `RefundGateway` |
| `web` | 공통 오류 응답 | `ApiExceptionHandler` |

## 데이터 모델


| 테이블              | 역할           | 주요 컬럼                                                                               |
| ---------------- | ------------ | ----------------------------------------------------------------------------------- |
| `room_inventory` | 객실 타입·날짜별 재고 | `room_type_id`, `stay_date`, `total`, `confirmed`, `held`                           |
| `reservation`    | 예약과 상태       | `request_key`, `room_type_id`, `check_in`, `check_out`, `status`, `hold_expires_at` |
| `payment_event`  | 처리한 결제 알림    | `payment_id`, `reservation_id`, `received_at`                                       |


체크아웃 날짜는 숙박일에 포함하지 않습니다. 11/10~11/12 예약은 11/10과 11/11의 재고를 사용합니다.

## API

### 예약 신청

```http
POST /reservations
Content-Type: application/json

{
  "requestKey": "req-abc",
  "roomTypeId": 1,
  "checkIn": "2030-11-10",
  "checkOut": "2030-11-12"
}
```

| 응답 | 조건 | 본문 또는 코드 |
|---|---|---|
| `201` | 새로 점유 | `{"id":1,"status":"HOLD","holdExpiresAt":"2030-11-02T01:10:00Z"}` |
| `200` | 같은 `requestKey` 재전송 | 기존 예약을 같은 형식으로 반환 |
| `409` | 점유 때문에 재고 없음 | `TEMPORARILY_HELD`, `Retry-After` 헤더 포함 |
| `409` | 확정으로 만실이거나 판매하지 않는 날짜 포함 | `SOLD_OUT` |
| `400` | 입력 오류, 당일 또는 지난 날짜, 체크인이 체크아웃보다 늦음, 30박 초과 | `INVALID_REQUEST` |

### 결제 성공 알림

```http
POST /payments/callback
Content-Type: application/json

{
  "paymentId": "pay-1",
  "reservationId": 1
}
```

| 응답 | 조건 | 본문 또는 코드 |
|---|---|---|
| `200` | 처리 완료 | `{"reservationId":1,"status":"CONFIRMED","duplicate":false}` |
| `200` | 이미 처리한 `paymentId` | 현재 상태와 `"duplicate":true` |
| `404` | 없는 예약 | `RESERVATION_NOT_FOUND` |

## 실행 방법

Docker가 필요합니다.

```bash
docker compose up -d --build
```

`8989` 포트로 실행되며, 데모용 디럭스룸(`roomTypeId: 1`) 재고가 2030-11-10, 2030-11-11에 1개씩 준비됩니다.

테스트는 Testcontainers로 실제 PostgreSQL을 띄워 실행합니다. 동시성은 인메모리 데이터베이스가 아닌 PostgreSQL에서 확인해야 하기 때문입니다. JDK 21과 Docker가 필요합니다. 재고 행 잠금을 제거하면 동시 신청 테스트가 실패하는 것을 확인했습니다.

```bash
./gradlew test
```

마지막 객실에 20건을 동시에 신청하는 데모는 다음과 같이 실행합니다. 다시 실행하려면 `docker compose down -v`로 재고를 초기화한 뒤 서버를 다시 띄웁니다.

```bash
./scripts/demo-concurrent-holds.sh
```

```text
== 예약 신청 20건 동시 전송
HOLD 1건, TEMPORARILY_HELD 19건
== 결제 성공 알림
{"reservationId":1,"status":"CONFIRMED","duplicate":false}
== 같은 결제 성공 알림 재수신
{"reservationId":1,"status":"CONFIRMED","duplicate":true}
== 확정 후 다른 고객 신청
{"code":"SOLD_OUT","message":"예약이 모두 찼습니다."}
```

## 한계

- 대형 OTA에서 같은 객실을 함께 판매하면 이 시스템만으로는 이중 판매를 막을 수 없습니다.
- 객실 고장처럼 확정 후 재고가 줄어드는 경우는 운영자가 직접 대응해야 합니다.
- 점유 만료 작업은 서버 1대를 기준으로 합니다.
- 결제 실패 알림은 받지 않으므로, 결제에 실패한 점유는 10분이 지나야 풀립니다.
- 결제 알림의 서명을 검증하지 않습니다. 실제 결제사를 연동하려면 위조 알림을 막는 검증이 필요합니다.
- 환불은 로그만 남기는 `RefundGateway` 구현체를 사용합니다. 실제 연동 시 외부 호출을 트랜잭션 밖으로 옮겨야 합니다.
- 같은 `requestKey`를 다른 내용으로 다시 보내도 기존 예약을 반환합니다.
- 같은 `paymentId`가 다른 예약으로 도착해도 중복으로 처리해 `200`을 반환합니다. 재고와 예약 상태는 바뀌지 않습니다.
- 연박 신청의 `Retry-After`는 기간이 겹치는 점유 중 가장 빠른 만료 시각 기준이라, 실제 대기 시간보다 짧을 수 있습니다.
- 체크인 다음 날 이후까지 결제 알림이 지연되면 재고가 남은 경우 지난 숙박이 확정될 수 있습니다. 당일 예약을 받지 않아 하루 이상 지연될 때만 발생하므로 별도로 처리하지 않습니다.

## 기술 스택

Kotlin, Spring Boot, Spring JDBC(`JdbcClient`), PostgreSQL, Flyway, JUnit 5, Testcontainers
